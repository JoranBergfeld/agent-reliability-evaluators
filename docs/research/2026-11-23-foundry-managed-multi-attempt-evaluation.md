# Foundry-managed multi-attempt reliability evaluation and reporting

Evidence date: **2026-11-23**. Research for [Verify Foundry-managed multi-attempt evaluation and reporting](https://github.com/JoranBergfeld/agent-reliability-evaluators/issues/11). Scope is current Microsoft Foundry, not Foundry classic. This is a document-and-source investigation, **not a live Foundry test**. No Azure operations were performed or charged. References to portal and API behavior below mean *documented* behavior, except the explicitly identified earlier prototype.

## Answer

**Partially plausible for calculation, not verified end-to-end for the required reporting.** Foundry's preview code evaluator runs a self-contained Python function once per evaluation item, reads item fields, and returns **one** float in [0, 1]. If all appropriate attempt evidence can be packaged into one accepted item, a deterministic paper-defined calculation within the sandbox is plausible; a nested or serialized grouped-evidence mapping to this evaluator has **not** been documented or demonstrated here. Foundry does not document a general cross-item, cross-run or cross-attempt reducer. The paper's metrics require different evidence and sometimes comparisons across tasks or conditions; a turn or an average of per-turn scores is not equivalent to those calculations. [C1][D1][P1]

The documented code-evaluator result has no return channel for a metric's unavailable state, reason, evidence counts or raw confidence/outcome pairs. It requires a pass threshold even when the customer wants measurement only, and the cloud results documentation describes threshold-based labels and pass-rate aggregates. Thus this surface **does not establish the requested non-misleading scorecard**. The portal documents scores and query-level details, but not how it renders grouped evidence, unavailable items, or raw observations; the aggregate statistic behind its Scores column for a custom continuous evaluator remains unspecified. [C1][R1][R2]

Preview is **accepted by the user for production** for this investigation; do not treat preview alone as a rejection or as GA. Microsoft labels code evaluators preview, requires the opt-in header in its documented definition examples, and warns that preview has no SLA and is not recommended by Microsoft for production. A stable SDK package does not change the service feature's status. The remaining barriers are the specific input and reporting contracts, not merely the preview label. [C1][V1][V2]

|---|---|---|

Arithmetic can be self-contained. **Inference:** a bounded valid multi-attempt statistic could be calculated if all required evidence reaches one call. [C1] | Neither a grouped-evidence code evaluator nor each paper metric has been executed or verified in Foundry. Correct formulas, data requirements and sample sufficiency still apply. |
| Repeated agent attempts | Foundry agent target can generate responses for dataset queries; Agent Framework's separate client-side `num_repetitions` runs each query independently; existing responses may also be supplied. [A1][A2][A3] | No documented native guarantee found for repeat count, reset/isolation, fault injection, identifier propagation and grouped collection into a single code-evaluator call. Never call agent APIs from sandbox code: network is unavailable. |
| Group all necessary evidence | JSONL/CSV or inline items, item schema and `{{item.field}}` mappings are documented; a versioned dataset can be reused. [D1] | Array-of-attempts schema, nested extraction, serialization and mapping into **code** `item` are unverified. Separate rows remain separate invocations. Cross-task metrics require the right task weighting, not an unverified run aggregate. |
| Per-metric value | One [0, 1] continuous float is documented, compatible in range with the paper's stated scores. [C1][P1] | Precision, NaN/infinity, boundary and serialization behavior are not specified; one return is insufficient for several independently meaningful values, counts or metadata. |
| Unavailable with reason and count | Exception/timeout yields 0.0 **and error** in the report, not a valid unavailable measurement. No documented null, skip, reason or count in the code return. [C1] | Need a distinct machine- and human-visible unavailable result, reason and valid/expected evidence counts; zero is a legitimate metric and cannot stand in for unavailable. |

[R2][D1] | Whether arbitrary grouped fields, full precision, pairing, provenance and identifiers survive output-item API and portal or exports is unverified. Dataset storage is not proof of scorecard visibility. |

[C1][R1] | An omitted acceptance criterion cannot be represented faithfully by inventing a threshold or “always pass”; confirm whether labels can be suppressed in every consumer. No common execution flow is assumed. |

Meaning of Scores for continuous custom evaluators, skip/reason/count rendering, and raw evidence visibility are unknown. |

The [paper metric definitions research artifact](https://github.com/JoranBergfeld/agent-reliability-evaluators/blob/40908939f4ae362a7a8bc5a0586ab845a8a586c1/docs/research/paper-reliability-metrics.md) inventories evidence and paper/code discrepancies. [Choose initial metric coverage and Foundry reuse boundaries](https://github.com/JoranBergfeld/agent-reliability-evaluators/issues/7) records a paper-first scope for all twelve with evidence-dependent availability; it does not establish that Foundry can run them. [Choose evidence inputs and unavailable-measurement semantics](https://github.com/JoranBergfeld/agent-reliability-evaluators/issues/2) records customer-defined sourced outcomes, post-completion confidence, customer operational constraints, and unavailable measurements with reasons and evidence counts. [Choose the per-metric reliability scorecard contract](https://github.com/JoranBergfeld/agent-reliability-evaluators/issues/5) records retaining and showing **every raw confidence paired with its outcome**, without added rounding; independently runnable metrics and optional grouping are a checkpoint, not a completed scorecard decision. No combined score or universal threshold is authorized.

[Foundry evaluator integration research](https://github.com/JoranBergfeld/agent-reliability-evaluators/blob/95da3fbfa12550c169b0523f678e825da1d40f17/docs/research/2026-11-22-foundry-evaluator-production-integration.md) identifies different local, managed-code, endpoint, and agent surfaces. Those are research conclusions, not proof that no undocumented alternative exists.

The [outcome consistency prototype](https://github.com/JoranBergfeld/agent-reliability-evaluators/blob/24cbe89/docs/prototypes/outcome-consistency-prototype.html) captured five Foundry agent responses to one synthetic task, each labelled successful; **1.00 was calculated locally**, not by Foundry. HTTP 429s occurred during exploration; interactive variations in the artifact are simulated. No native aggregation or metric publishing was demonstrated. [Prototype outcome consistency in Foundry](https://github.com/JoranBergfeld/agent-reliability-evaluators/issues/10) records resource-group deletion. Its human-confirmed prototype boundary does not settle whether a different managed-code integration could work.

## Grouping and mapping: the key experiment

**Documented:** a JSONL line is an evaluation test case; uploaded JSONL/CSV and inline `file_content` are supported. The dataset sample defines `data_source_config.item_schema` and `testing_criteria[].data_mapping` using `{{item.query}}`-style expressions. Each evaluator is executed on each row. The code-evaluator guide separately shows `definition.data_schema` with an `item` object and `grade` reading `item.get("response")`; the target-generated output is at `item.get("sample", {}).get("output_text")`, a documented access pattern explicitly subject to change. These are separate namespaces and configurations; they should not be conflated. [D1][C1]

**Candidate, not a verified Foundry contract:** construct one row for an entire *metric input unit*, rather than one row per attempt. For example, a row could carry a `query`/`response` required for a dataset scenario plus `task_id`, `condition`, definition/version and an `attempts` JSON array or `attempts_json` string containing attempt identifiers, outcomes, outcome source and optional confidence. Declare those fields in the dataset schema and evaluator's `data_schema`, then test access via `item.get(...)` and, where required, a `data_mapping` such as `{"attempts_json":"{{item.attempts_json}}"}`. The published examples document scalar mappings, **not** that nested arrays or the string pass unchanged through every validation/mapping layer. The code example omits `data_mapping`, while the general dataset guide says to map required fields. Whether original fields, mapped fields, or both reach `grade` must be measured, including escaping, missing fields and type preservation. [C1][D1][S1]

Illustrative logical evidence only (not a submitted JSONL, nor a claim that schema is accepted):

```json
{
  "task_id": "T1",
  "condition": "baseline",
  "attempts": [
    {"attempt_id": "a1", "outcome": 1, "outcome_source": "customer-test", "confidence": 0.83},
    {"attempt_id": "a2", "outcome": 0, "outcome_source": "customer-test", "confidence": 0.67}
  ]
}
```

In the paper's outcome-consistency definition, four outcomes `[1, 1, 1, 0]` yield per-task `(2 × 3/4 − 1)² = 0.25`; another task `[1, 1, 1, 1]` yields 1.0; the equal-task paper aggregate is 0.625. If each task becomes a row, **0.625 cannot be assumed to be the displayed aggregate**: the cloud documentation describes a pass rate, not this arithmetic mean. A single item containing both tasks could calculate it, contingent on the mapping and limits. Unequal repetitions make averaging per-attempt labels especially inappropriate; missing, duplicate or wrong-condition evidence must not silently become failures or zeroes. This arithmetic example is an offline derivation from [P1], not an observed Foundry result.

Different evaluators may need different grouping keys and units: task/attempt for outcome or trajectories; per-task resource observations before equal-task aggregation; baseline and perturbation conditions for robustness; confidence and sourced outcome pairs for calibration/discrimination; rule-linked violations and severities for safety. Group only what each metric needs; do not require safety data to run outcome consistency, or require an agent invocation if evidence is supplied. Grouping by a concatenated conversation is not automatically equivalent to repeated independent attempts, and conversation-level code evaluators are skipped. [P1][C1]

## Attempt collection and execution boundaries

1. **Foundry-run target:** `azure_ai_target_completions` with an `azure_ai_agent` target sends query items to prompt or hosted agents and evaluates generated responses. The target's generated response is not a group of independent attempts. Repeating rows or runs is a possible *experiment*, not a documented repeat-and-reduce capability or proof of isolation; pin agent versions and collect stable task, condition and attempt identities. [A1]
2. **External orchestration:** Agent Framework documents Python `evaluate_agent(..., num_repetitions=3)` and .NET `numRepetitions` as independently running each query and producing three items; this is client/framework orchestration, not a Foundry code-sandbox agent call or evidence of cross-item reduction. A caller could instead make repeated Responses calls and gather evidence, without assuming any one orchestrator. State reset, tool/environment controls, confidence elicitation, provenance and error handling must be designed and verified for the agent. [A2]
3. **Supplied evidence:** Foundry dataset evaluation can assess precomputed inputs. Foundry can also evaluate stored agent responses with `azure_ai_responses`; the current guide says `file_content` only for response IDs, with `file_id` rejected. Response IDs alone do not supply all sourced outcomes, confidence, resource measures or condition relationships needed for reliability. [D1][A3]
4. **Judging and failures:** outcomes and confidence must be provided or produced by an appropriate separate component. A task-success judge is not an acceptance criterion; response text alone must not be presumed ground truth. Missing attempted calls, parse failures, 429s, duplicates and partially captured traces require explicit provenance and counts, not fabricated observations. Fault/perturbation exposure and environment reset are not established by the evaluation service sources.

## Runtime, limits, numeric behavior and versions

* **Managed code:** `grade(sample: dict, item: dict) -> float`, continuous 0.0–1.0, higher-is-better; turn-level only. Under 256 KB code, 120 seconds per grading call, 2 GB memory, 1 GB disk, 2 CPU cores, and **no network**. Available versions include numpy 2.2.4, scipy 1.15.2, pandas 2.2.3 and scikit-learn 1.6.1; the full list and preloaded NLTK corpora are in [C1]. No runtime Python version, arbitrary package installation, state reuse/isolation, deterministic scheduling or retry guarantees are stated there. A valid project model `deployment_name` and `pass_threshold` are required even though code makes no LLM call. [C1]
* **Input sizing:** evaluation rows have a documented **2 MB maximum** and batch evaluations 100,000 rows. Grouping many full traces/raw pairs in one row trades reducer availability for a hard row limit; chunking would itself require a correct cross-chunk reduction, which is not established. Run-creation rate limits span tenant, subscription and project, with `retry-after`; feature/region limits also apply. [L1]
* **Precision:** the paper states final scores in [0, 1], but a native float does not prove lossless decimal or display precision, and raw ratings cannot be recovered from a score or bin counts. Test values close together and bin boundaries, preserve original raw representations and provenance, and do not infer equality or rounding policy from a portal display. JSON numeric precision, double encoding, rounding of returned scores, `NaN`/infinity and integer overflow acceptance are **unverified**. No unsupported arbitrary score domain is assumed. [P1][C1]
* **SDK/API cross-check:** [C1] specifies `azure-ai-projects>=2.8.0`; [E1] specifies `>=2.11.0` for endpoint evaluator examples. On 2026-11-23 [V1] reports `azure-ai-projects` 2.11.0, published 2026-11-13, Python >=3.10, `openai>=3.0.0`; [V2] reports `azure-ai-evaluation` 1.18.12, published 2026-11-12, Python >=3.9, `openai>=1.108.0`. These are package requirements, **not** the managed evaluator runtime Python version or feature GA claims. The Evals [REST reference](https://learn.microsoft.com/en-us/rest/api/microsoft-foundry/azureopenai/evals) identifies API `v1` for that surface; this does not establish the evaluator-definition API version.
* **Source discrepancy:** the official guide's code registration declares a `continuous` 0–1 metric, numeric threshold and preview header [C1]; Microsoft's tagged [2.11.0 sample](https://raw.githubusercontent.com/Azure/azure-sdk-for-python/refs/tags/azure-ai-projects_2.11.0/sdk/ai/azure-ai-projects/samples/evaluations/sample_eval_catalog_code_based_evaluators.py) instead declares `ordinal`, a string threshold schema while supplying 0.5, and omits the header. The sample also has no explicit mapping. Do not silently interpret these as interchangeable: use the guide as the stated contract and validate the actual service/version.

## What reporting surfaces actually promise

**Cloud API.** Evaluation runs are asynchronous; `evals.runs.retrieve` returns status and `report_url`, and `evals.runs.output_items.list` retrieves paginated item results. [R1] shows an item with `score`, `label`, `threshold`, `passed` and optional evaluator-specific reason/details; its documented run aggregate is `result_counts` and per-criterion `passed`, `failed`, `pass_rate`. These counts are **evaluation-item verdict counts**, not necessarily valid/expected attempts, calibration bin counts or a paper metric. An API-retrieved row score may be useful, but a mandatory verdict can mislead if no acceptance criterion was set. Do not assume input fields are echoed, error zero is excluded from aggregate or arbitrary details survive. [R1]

**Current portal.** [R2] describes Evaluation run list, dataset download as CSV, scores per evaluator, and run details containing query, response, ground truth, score and explanation. Compare uses statistical t-tests and direction-based labels. It does not specify the formula behind continuous custom evaluator Scores, whether or how scorecard-specific reasons, raw pairs or counts render, or how erroneous/skipped items enter comparisons. A rendered number, `report_url`, downloadable input or Compare t-test is not proof of the required metric semantics, nor a substitute for raw evidence.

**Alternative endpoint evaluator, not Foundry-managed calculation.** Preview schema `0.0.2` POSTs one item to a **customer-operated** HTTP endpoint; the original row is in `context` for dataset, model-target and agent-target runs, but not trace/simulation/stored-response runs. Version 0.0.2 ignores `data_mapping`; 0.0.1 supports it. A completed result requires numeric `score` and boolean `passed`; `skipped` can carry `reason` without a score; `properties` can hold evaluator-specific data, while `dimension_scores` has special 1–5/null restrictions. Only one registered ordinal or continuous metric is permitted; unknown top-level response fields are rejected, and the endpoint must answer within 120 seconds. Portal-created definitions might use 0.0.1. [E1] This contract provides a candidate for unavailable-with-reason and counts/pairs in `properties`, but does **not** prove API or portal preservation/display, skip aggregation, or no misleading verdict. It also does not meet the preferred Foundry-managed compute requirement. Do not decide a fallback here.

**Local SDK upload is a separate, unproven reporting path.** [Foundry SDK metrics reporting research](https://github.com/JoranBergfeld/agent-reliability-evaluators/blob/e5e9460e6287b96191cbc335f5538ee43ac0b95f/docs/research/2026-11-22-foundry-sdk-metrics-reporting.md) inspected `azure-ai-evaluation` 1.18.12 source: its project-endpoint upload uses internal preview `2025-11-15-preview` plumbing, aggregates numeric columns and leaves string reasons outside aggregate metrics. Its current-portal visibility/support was not verified. The Learn local-evaluation article is [classic-only](https://learn.microsoft.com/en-us/azure/foundry-classic/how-to/develop/evaluate-sdk); neither it nor storing a dataset demonstrates current-portal publication. This is a possible future probe, not the requested managed calculator or a product decision.

## Unresolved checks for a separately approved live probe

No experiment below was performed; execution requires separate permission for Azure operations and cost. Use disposable resources, budget/rate limits, and cleanup, recording project region, actual SDK/API versions, evaluator definition, run IDs and timestamp. Distinguish documented behavior from measured behavior:

1. **Mapping:** register a preview code evaluator, first with a scalar string and then a JSON-encoded grouped string and nested array. Try documented data schema plus mapping, and compare `grade`-visible values against submitted data; test inline/file JSONL, missing/null/extra fields, Unicode/escaping and size near the 2 MB limit. Establish which shapes and mappings succeed, not just registration.
2. **Reduction and selection:** supply multiple task groups including the 0.25/1.0 example. Verify each item's score and whether a whole-campaign item can compute 0.625. Compare output to portal Scores and API aggregates, and evaluate each metric independently and multiple metrics together using differing evidence fields. Test an unconfigured evaluator separately from one with missing evidence. Do not interpret pass rate as metric mean.
3. **Unavailable and errors:** use missing outcomes, too few observations, invalid confidence, no violations and mathematically undefined denominators. Capture `grade` exception/timeout behavior, actual status and scores, labels and aggregate inclusion. Do not claim a truthful unavailable result if only 0.0/error is present.
4. **Raw evidence and numeric fidelity:** submit distinct confidence/outcome pairs including adjacent decimal values and bin boundaries. Retrieve all output-item pages, original dataset/export and portal details; compare raw values, pair identities, reasons and evidence counts byte-for-byte or numerically at recorded precision. Check whether a customer without dataset access can actually see them.
5. **Threshold semantics:** run with a customer-chosen criterion and with no criterion if the service permits; inspect item labels, run counts, portal comparison and exports. A forced neutral or always-pass threshold is **not** a valid measurement-only result. Check unavailable separately.
6. **Attempts and context:** compare client-orchestrated repeats, separately submitted precomputed evidence and Foundry target repetitions; trace IDs, task/condition/attempt identities and agent version, capture 429/retries, and independently test reset/isolation and perturbation exposure. Do not assume a sandbox network connection or equate conversation turns to attempts.
7. **If authorized separately**, probe endpoint 0.0.2 skipped reason and arbitrary `properties` visibility and skip denominators; probe the private local-SDK upload route only with an explicit support caveat. Neither result should be represented as Foundry-managed code execution.
