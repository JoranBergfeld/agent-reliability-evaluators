# Foundry evaluator coverage and experiment extension points

Evidence date: **2026-11-17**. Research ticket: [#4](https://github.com/JoranBergfeld/agent-reliability-evaluators/issues/4). Parent: [#1](https://github.com/JoranBergfeld/agent-reliability-evaluators/issues/1). Repository baseline: `d0312c1`.

## Answer and boundaries

**No exact, end-to-end native implementation of any of the twelve paper metrics was verified in the inspected Foundry catalog and SDK references.** This is a bounded documentation finding, not proof that no other service feature exists. Foundry provides substantial reusable evidence, judging, execution and reporting facilities; it would be wasteful to rebuild those without first checking semantic and integration fit. Eight metrics have identifiable partial building blocks; four have a custom measurement gap beyond generic evaluator extensibility. Every metric still needs either custom calculation, experiment handling, evidence interpretation, or some combination. [P; C; A; R; T; O]

In particular:

- Task Completion is a possible **task outcome source**, not outcome consistency.
- Task Navigation Efficiency compares a run with an expected path, not pairs of repeated runs.
- Tool Call Success diagnoses technical tool failures, not task-success retention under injected faults.
- Task Adherence and Prohibited Actions can help detect operational constraint violations. Content-safety severity is **not** operational harm severity.
- Microsoft now documents Agent Framework repetition support; it is an execution building block, not the paper's consistency calculation.
- Local Python callables and hosted custom evaluators are different contracts. Hosted row/conversation scoring is not an experiment-wide reducer.
- Several current documents contradict one another on custom evaluator conversation support and schema details. Those paths remain **unverified**, not implementation promises. [A; R; H; E; F; V]

This note supports subsequent decisions; it does not select packaging, final architecture, evidence providers, first-release metrics, or customer acceptance criteria. All twelve measurements remain exposed conceptually. No aggregate reliability score, pillar score, or universal acceptance threshold is proposed. “Rubric” in the product request means a reliability scorecard; it does not automatically mean Foundry's weighted Rubric evaluator.

Research was documentation/source inspection only. No Azure resource provisioning, new authentication, evaluation execution, agent deployment, or billable experiment was performed.

## 2. Per-metric semantic coverage matrix

Definitions below summarize **Table 2 of paper v3** only far enough to compare Foundry semantics. Exhaustive paper analysis is a separate workstream. No paper aggregate scores are included.

Verdicts:

- **Exact/native**: a documented built-in produces the same measurement from the required evidence with matching population, grouping and reduction. None verified.
- **Partial building block**: documented evidence, judge or execution support is useful, but is not the complete metric.
- **Custom gap**: the inspected catalog has no corresponding specialized measurement; generic custom scoring does not count as native coverage.
- **Unverified**: material support cannot be established, including contradictory documentation. Specific unknowns are identified in the last column and section 7 rather than silently promoted to coverage.

“Partial” describes the strongest reusable facility, not permission to substitute its score for the paper metric. Coverage verdicts and remaining-work statements are research inferences from the cited paper definitions and documented platform contracts, not Microsoft claims of paper compatibility.

| # / metric | Paper evidence and reduction [P] | Strongest documented Foundry reuse | Verdict and remaining work / uncertainty |
| --- | --- | --- | --- |
| 1. Outcome consistency, `C_out` | Binary outcomes for K repeats of each task; per-task success fraction p; average `(2p-1)^2` across tasks. Always failing is consistent too. | Task Completion (preview) is a binary end-to-end judge; local outcome checks are possible. Framework `num_repetitions` executes independent repeats. [A; E; F] | **Partial building block.** Validate outcome judging against the task-success definition; retain task/repetition identity and calculate per-task statistic before task averaging. Neither overall success/pass rate nor a single completion score is consistency. K=1 cannot reveal repeat variability. |
| 2. Distributional trajectory consistency, `C_traj^d` | Per-run action-type frequency distributions; one minus mean pairwise Jensen-Shannon divergence within a task, then across tasks. | Structured tool messages and OTel `execute_tool` spans provide action evidence. [T; B; Q] | **Partial building block.** Custom action taxonomy, run reconstruction, distribution normalization, pairwise divergence and grouped reduction. Tool Call Accuracy/Selection assess correctness/necessity, not distribution similarity across repeats. Unobserved actions cannot be reconstructed just from final text. [A] |
| 3. Sequential trajectory consistency, `C_traj^s` | One minus pairwise normalized Levenshtein distance on repeated action sequences; normalize by the larger sequence length, average pairs/tasks. | Ordered tool interactions/spans; Task Navigation Efficiency supplies a distinct expected-path diagnostic. [A; B] | **Partial building block.** Extract canonical ordered action sequences and implement pairwise distance/reduction. Matching an “optimal” reference sequence is not matching repeated trajectories. A tool-only trace might not represent all paper/customer actions; parallel span ordering and empty sequences need explicit handling. |
| 4. Resource consistency, `C_res` | Resource values across repeats, coefficients of variation `sigma/mean`, resource-type averaging and exponential transform. | Tracing records duration, token consumption, tool use/retries and cost signals. Model-target evaluation also reports optional p50/p95 target latency and estimated model cost. [B; O] | **Partial building block.** Need per-attempt, consistently scoped resources, not just run-wide percentiles/totals; custom variability calculation. Cost estimates can be missing/partial and model-target-only; no promise of full agent/tool bill. Separate agent resource consumption from evaluator/judge overhead. Zero resource means and task weighting require a declared policy aligned with paper analysis. |
| 5. Fault robustness, `R_fault` | Matched task population at baseline and under injected faults; `min(Acc_fault/Acc_baseline,1)`. | Target execution, outcome judges and result export; Tool Call Success detects technical errors. Function middleware can override customer-owned function execution/results. [T; A; O; M] | **Partial building block.** Fault schedule/injection, safe/resettable execution, baseline matching, condition labels and success-ratio reduction remain custom. A technically failed tool can be recovered by the agent: tool-failure rate is not task robustness. No generic hosted evaluation parameter implementing the paper's fault protocol was documented in inspected sources. |
| 6. Environment robustness, `R_env` | Baseline versus semantic-preserving environment/tool-interface changes; clamped task-accuracy ratio. | Versioned prompt-agent tool configuration; custom function implementations/middleware; versioned datasets and target selection. [J; M; D; T] | **Partial building block.** Generate controlled interface/format/environment variants, preserve semantics and initial state, execute conditions and calculate ratio. Evaluator mappings transform grading inputs, not the environment seen by the agent. Changes to tool descriptions alone do not prove environment robustness. |
| 7. Prompt robustness, `R_prompt` | Baseline task success versus semantically equivalent prompt paraphrases; clamped accuracy ratio. | Dataset input fields/message templates and versioned agent instructions support varied queries/configuration. Framework repetitions and target evaluation can execute them. [D; T; J; F] | **Partial building block.** Need paraphrase construction/validation, variant-to-task linkage and paired-condition reduction. Text Similarity is not task-success retention; optimizer-generated “better” instructions are not guaranteed equivalent paraphrases. [C; Y] |
| 8. Calibration, `P_cal` | Agent confidence c and binary outcome y; `1 - ECE`, using confidence bins and bin-size-weighted absolute confidence/accuracy differences. | Custom dataset schemas can carry supplied confidence/outcome; custom evaluators can read them. [D; H; E] | **Custom gap.** No native ECE/calibration metric or general agent success-confidence source verified in catalog. Need confidence elicitation/import, binning, pooled evidence and custom reduction. Averaging per-row absolute errors is not binned ECE. |
| 9. Discrimination, `P_AUROC` | Confidence/outcome pairs from successes and failures; compare confidence across success-failure pairs. | Same generic dataset/custom-evaluator transport. [D; H; E] | **Custom gap.** Need population-level calculation; a row has no AUROC. Table 2 uses strict `c_success > c_failure`; standard AUROC libraries commonly credit ties differently, so do not substitute a library blindly. No-class populations/ties require reconciliation with paper analysis. No native confidence-discrimination evaluator verified. [P; C] |
| 10. Brier, `P_brier` | `1 - mean((c-y)^2)` on agent success confidence and binary task outcomes. | Local numeric mean aggregation can reduce a **custom** per-row `1-(c-y)^2` score. Hosted code can produce that row score too. [L; H] | **Custom gap**, but straightforward reusable mean machinery locally when rows/weights match the paper population. Not a built-in Brier evaluator. Hosted aggregate **pass rate** is not the mean Brier score; retrieve raw scores for the proper reduction. Neither judge confidence nor normalized quality Likert scores are agent success confidence. [O; A] |
| 11. Constraint compliance, `S_comp` | Fraction of tasks with an empty violation set for declared operational constraints, regardless of immediate harm. | Task Adherence (preview) judges system rules/policy; Prohibited Actions (preview) addresses explicitly disallowed behavior/tool use; Sensitive Data Leakage addresses a subset of constraints. [A; R] | **Partial building block.** Potentially exact predicate reuse for a particular validated constraint set, but not a verified general native equivalent. Need task-wide violation evidence and “any violation” reduction. Adherence and the agent safety evaluators are turn-level; Prohibited Actions/leakage are agent-target-only, not dataset/model evaluations. Do not equate content defect rates with all operational violations. |
| 12. Harm severity, `S_harm` | On violating tasks only, take each task's maximum violation weight (low .25, medium .5, high 1), then one minus their conditional mean. | Custom prompts/endpoints can judge supplied violation/impact evidence. Safety detectors may contribute violation flags, not this severity calculation. [H; R] | **Custom gap.** Need domain-grounded violation severities and task linkage, max-within-task and conditional reduction. No documented native operational-consequence severity with the paper's weights/conditioning verified. Content-safety 0–7 intensity is a different construct. No violations is an undefined conditional population unless the chosen metric convention explicitly addresses it; do not silently manufacture a perfect score. |

**Inference from the matrix:** using built-in Task Completion or Task Adherence is promising only after checking that the task-success/constraint definition is observable in the provided transcript and covered by the evaluator. A fluent claim that a refund happened does not establish a correct database mutation. This is a limitation of available evidence, not a requirement that every customer implement a business-aware judge.

## 3. Local versus hosted custom evaluator contracts

### Documented facts

| Execution surface | Input/output and granularity | Important constraints |
| --- | --- | --- |
| Local `azure-ai-evaluation` | Function or callable class; e.g. `__call__(*, response, **kwargs)` returning named score fields, or scalar-returning function. `evaluate(data=..., target=..., evaluators=..., evaluator_config=...)` maps dataset/target output columns into evaluator arguments. Results include row data and metric summaries; optional project logging. [E; L] | Local orchestration does **not** mean all judging is offline/free: model/safety evaluators call services. Pure code checks can run locally without those calls. Tagged implementation generally averages numeric output columns, with special content-safety/label/binary handling; it does not expose a documented arbitrary cross-row reducer argument. [E; L] |
| Hosted code custom evaluator (preview) | `grade(sample: dict, item: dict) -> float`, one float in `[0,1]`, higher is better. Dataset fields read from `item`; generated target text currently accessed through `item["sample"]["output_text"]` per the custom guide, explicitly subject to change. [H] | Code `<256 KB`; 2 minutes per grading call; no network; 2 GB memory, 1 GB disk, 2 CPUs. Available packages include NumPy **2.2.4**, SciPy **1.15.2**, pandas **2.2.3**, scikit-learn **1.6.1**, rapidfuzz **3.10.1**. Error/timeout is recorded as **0.0 plus error**, not clean task failure. Code requires `pass_threshold` and even a valid `deployment_name` for orchestration despite no LLM call. [H] |
| Hosted prompt custom evaluator (preview) | Judge template with mapped fields; output JSON `result` and `reason`. Binary, ordinal integer, or continuous scoring with declared range. Requires `deployment_name` and `threshold`. [H] | Model inference and rubric validity affect measurement. Newer REST says exactly one supported evaluation level, turn or conversation. This does not grant dataset-wide state. [V] |
| Hosted endpoint custom evaluator (preview in catalog) | Customer-operated POST service via project connection. Version **0.0.1** request has evaluator name/version, `evaluation_level`, `data.item` mapped data and optional `data.sample`. Output has nullable numeric/bool `score`, `reason`, execution `status`, optional `properties`, threshold/passed and error fields. [H] | API-key or Entra/project-managed-identity authentication; guide requires a response within **30 seconds**. REST now lists **0.0.2** too, but this note did not establish its complete contract. Guide mentions item or batch calls; REST describes each evaluation row. Neither establishes whole-experiment delivery or ordering. [H; V] |
| Agent Framework local/custom provider | `EvalItem` wraps conversation/tools/context; decorated checks can receive named fields and return bool, float, dictionary or `CheckResult`; asynchronous functions supported. `FoundryEvals` supplies hosted judging. [F] | Framework documentation interprets floats `>=0.5` as passing, and examples assert all passed. Those convenience gates are not this product's customer acceptance criteria. Article lacks a numeric SDK pin; compatibility needs a later validation. [F] |

**Inference:** a generic hosted code evaluator cannot fetch missing traces/database outcomes or stitch prior rows via network, and no global ordering/state guarantee is documented. An external endpoint permits network access but does not, by itself, solve concurrency-safe experiment grouping. If repeated runs are deliberately packed as an array into one custom item, that could enable grouped code calculation, subject to schema/size/runtime constraints; this is a possible adaptation, **not verified native dataset-level reduction**. It also must not be confused with the contradictory conversation-level support discussed below. [H; V; X]

**Scorecard constraint:** several hosted paths demand thresholds and report labels even when the desired deliverable is raw measurements. Preserve raw metric values and execution status independently; do not turn a service initialization threshold or default pass label into a universal reliability acceptance criterion. Whether all hosted UI/endpoint paths can omit or suppress labels remains unverified. The endpoint schema allows nullable threshold/passed, whereas hosted code/prompt guide examples require thresholds. [H; O]

## 4. Rows, conversations, experiments and grouping

### Documented facts

1. Foundry Evals separates the evaluation definition (`data_source_config` and `testing_criteria`) from named execution runs. Multiple runs can use the same definition; datasets have reusable versions. Runs have identifiers and can carry metadata, as demonstrated by trace evaluation examples. Results can be paginated and retrieved per item, in addition to run-level pass counts/rates. [D; T; Q; O]
2. An evaluation **turn** and a complete **conversation** are different units. Conversation data uses a full `messages` array. The run's `evaluation_level` defaults to turn; incompatible turn-only evaluators can be **skipped** in conversation runs. Conversation support therefore does not imply a successful full-task constraint check from every evaluator. [C; N]
3. Agent Framework `evaluate_agent(..., num_repetitions=3)` explicitly produces independent repetitions, with three items per query. The documentation calls this a consistency workflow, but does not document the paper's statistic or a complete repeated-task identity schema. [F]
4. Local `evaluate` exposes string tags; source aggregation generally means numeric columns and separately calculates some pass/defect rates. Hosted aggregate results document passing rates, not arbitrary task-grouped statistics. [L; O]

### Implications, not an architecture decision

- At least outcome/trajectory/resource consistency require membership of each attempt in a task's repeat group. Robustness requires task/population alignment between baseline and each condition. Calibration/discrimination require the confidence/outcome population, and harm requires a violation-conditioned population. Run IDs and conversation IDs help correlation but do not define those experimental relationships. [P]
- Candidate evidence fields include `experiment_id`, stable `task_id`, `attempt_id`/repetition index, condition and variant IDs, agent/configuration version, initial-state/reset identifier, response/trace ID, outcome source/version, confidence elicitation version, constraint/severity policy version, and evidence completeness/error status. These are **derived requirements to investigate**, not a decided public API or mandated storage design.
- Calculate each paper statistic at its specified grouping before reducing. Pooling every response or averaging condition ratios arbitrarily can change task weighting. A platform report's pass rate is not automatically a reliability metric.
- Preserve acquisition/execution errors, missing evidence and evaluator errors separately from binary task failure. In particular, hosted grader error-as-zero and skipped/absent outputs can distort denominators if treated as normal scores. [H; N; L]
- Repetition support does not promise deterministic seeds, reset external state, or neutralize memory/caches. These are experiment controls, not guaranteed by a score function. Nothing in the inspected Evals target contract documents a generic reset or fault-injection hook. [F; T]

## 5. Traces, resource evidence, confidence and outcomes

### Traces/resources: documented support

Foundry tracing uses Application Insights/OTel for input/output, tools, retries, token consumption and timing, with custom span attributes and trace hierarchy. It documents `invoke_agent`, `execute_tool`, tool definitions, call arguments and results. Framework integrations include Microsoft Agent Framework, Semantic Kernel, LangChain/LangGraph and OpenAI Agents SDK; LangChain/LangGraph integration here is Python-only. Prompt/hosted tracing is GA; external/workflow tracing is preview. GenAI semantic conventions are still Development status. [B]

Trace evaluation (preview) retrieves recorded interactions without replaying them. It supports explicit trace IDs (`operation_Id`) or agent/time filtering; `gen_ai.conversation.id` can correlate conversations. Relevant input/output message attributes and tool definitions must be emitted. Missing input/output messages can produce `score=None` for quality evaluators. Missing tool schemas may be inferred incompletely. The service and user also need appropriate Application Insights/Log Analytics permissions. This is not evidence that arbitrary span attributes, resource counters or final database state are automatically passed to every custom evaluator. [Q]

Trace content recording is configurable and can expose sensitive user/tool data; retention/sampling apply. “Intelligent sampling” explicitly deduplicates traces and filters broken/truncated/malformed sessions before diversity selection. These documented behaviors may be useful for quality review but are **not a neutral repeated-run sample**. [B; Q]

Cloud results now provide optional **run-wide** `latency.target` p50/p95/sample_count and `estimated_cost.target`, including completeness and unpriced models. Cost availability is documented for **model-target**, Global Standard deployments with usable token attribution/pricing. It is not guaranteed for agent targets or all resource types. Percentiles and a total cost cannot recover per-task repeat CV. [O]

**Inference:** trajectory/resource metrics may reuse instrumentation/export, but need an evidence completeness policy, target-only attribution and raw per-attempt measurements. Sampling, hidden tool execution, disabled content capture, concurrent spans and missing external costs can invalidate an apparent measurement. A trace display is not proof that all physical side effects are observed.

### Outcomes/confidence: keep sources undecided

**Documented:** Task Completion judges whether a usable deliverable meets the request, with turn and conversation support; Task Adherence evaluates actions against instructions and constraints, currently turn-level. Agent evaluators consume mapped query/response/messages and sometimes tool definitions. Tool support is constrained: File Search, user-defined Function Tool, MCP and Knowledge-based MCP are supported; the guide cautions against several tool/groundedness evaluators with Azure AI Search, Bing grounding/custom search, SharePoint grounding, Code Interpreter, Fabric Data Agent and Web Search. [A]

**Inference:** these are candidate evidence interpreters, not a universal oracle of customer business outcomes. Reusable alternatives to investigate include existing benchmark/task validators, recorded authoritative state/results, task-specific deterministic assertions, human labels, built-in judges and custom judges. This list does not choose who supplies them. The correct source depends on what the customer task-success definition actually requires.

**Documented paper practice:** confidence is post-hoc agent self-assessment after completion. None of the inspected Foundry catalogs or contracts establishes automatic extraction of a calibrated probability that the customer's agent completed its task. [P; C; A; H]

**Inference:** success confidence must be explicitly obtained/imported with provenance and joined to the appropriate outcome. An evaluator's confidence property, a model token log probability or a 1–5 quality score is not interchangeable with that success probability. Elicitation itself can alter prompts/costs, so whether and how to collect it remains a decision.

**Operational safety:** Prohibited Actions is closer than generic content safety because its definition names disallowed actions/tool uses and user-verified policy. But docs restrict it and Sensitive Data Leakage to agent targets, turn-level, with no dataset/model use. The inspected page does not establish arbitrary policy injection, exact violation-set output or operational severity mapping for every customer domain. Task Adherence can also help, but transcript-only judgments cannot verify unrecorded consequences. Content-safety 0–7 severity evaluates harmful language, not the paper's max-weight operational consequences conditioned on violating tasks. [R; A; P]

## 6. Customer-agent integration and controlled experiment seams

These are supported boundaries and plausible adaptations, **not a selected execution architecture**.

## 7. Unverified support, contradictions and next evidence

These are technical evidence gaps, not decisions on human/product tickets.

1. **Custom code conversation support conflicts.** H explicitly describes `evaluation_level="conversation"` and `grade()` reading `item["messages"]`. The newer V says custom code supports **only turn**, and prompt supports exactly one level. Treat hosted code conversation support as **unverified**; resolve against an explicitly selected SDK/service contract and later nonproduction contract test. Neither statement establishes cross-task/dataset aggregation.
2. **Custom schema drift.** H registers `init_parameters`, `data_schema`, and `metrics` inside evaluator definitions. V's displayed code/prompt definitions omit these fields and require `evaluator_type`; endpoint schema versions expand to `0.0.2`. Do not assume guide payloads and newest REST schema are interchangeable. Exact `api-version` for that REST operation and the full `0.0.2` endpoint payload remain unverified. [H; V]
3. **Rubric drift.** U describes weighted 1–5 quality dimensions, a normalized overall score, default threshold .5 and per-dimension details. V now additionally distinguishes Boolean safety rubrics with allowed/disallowed dimensions and two independent lower-is-better metrics, **no combined safety score/threshold**. Those newer safety outputs could be useful violation evidence, but no verified mapping to arbitrary task violation sets or the paper's conditional harm weights was established. Do not mistake ordinary quality Rubric for the requested statistical reliability scorecard. [U; V]
4. **Catalog freshness.** C lists Quality Grader as preview, while A explicitly says deprecated and no longer runnable. A also describes composite and individual evaluator levels separately. Do not rely on broad catalog labels where a specific evaluator's documentation disagrees; later enumerate the actual versioned catalog for the chosen environment. No live catalog query was performed. [C; A]
5. **Trace mapping inconsistency.** Q prose says to omit `item.`/`sample.` prefixes for extracted fields, but its variable table and code use `{{item.query}}`/`{{item.response}}`. Exact mapping behavior must be checked when pinning a contract. Custom access to arbitrary span attributes/resource counters is not established by its conversation extraction examples. [Q]
6. **Grouping guarantees.** Framework repetition exists, but exact stable task/attempt metadata, retries, state/session isolation and reproducibility guarantees need source-level/versioned confirmation. Hosted row endpoint batch wording does not establish delivery of an entire experiment. [F; H; V]
7. **Evidence validity.** No chosen source for task outcomes, confidence, constraint sets or operational impact exists yet. Built-in judge compatibility with a given customer's tools/tasks and availability of authoritative state must be established before calling any measurement complete. Automated judged failure and evidence-collection failure are not synonymous. [A; R; P]
8. **Operational availability.** Limits are 2 MB per row/100,000 rows per batch; endpoint and sandbox timeouts differ. Regional tables cover batch, safety and other workflows differently, and do not explicitly enumerate Prohibited Actions/leakage in their safety region table. Availability for these preview evaluators, VNet endpoint reachability, quotas and threshold-free presentation need confirmation for the eventual environment. [X; H; R]
9. **Paper calculation edge cases.** Exact CV task reduction/variance conventions, zero baseline accuracy, empty trajectories, no violating tasks, missing confidences and AUROC ties/one-class populations must align with the exhaustive paper analysis rather than accidental library defaults. This note identifies the dependence without inventing numerical conventions. [P]

## 8. Decision-useful conclusion

**Supported conclusion:** reuse Foundry's applicable built-in outcome/constraint/tool judges, trace collection, dataset versioning, execution/repetition facilities and raw results where they genuinely fit. Plan for custom experiment semantics and metric calculation; do not scope the work as twelve per-response judge prompts. Confidence, authoritative outcomes and operational impact are evidence problems as well as formulas. [Matrix; sections 3–7]

**Not concluded:** which metrics ship first; whether evidence is imported, generated live or trace-derived; who supplies labels/judges; local versus hosted packaging; whether a reducer belongs in a client, service or pre-grouped dataset; acceptance criteria; or any final product architecture. These remain inputs to the parent map's decisions, followed by `/to-spec` and `/to-tickets`.
